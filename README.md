# Проверка условий договоров поставки — прототип

Локальное приложение для специалиста по закупкам. Пользователь загружает TXT-файлы (договоры, допсоглашения, письма, проекты) и получает таблицу по договорам: номер, поставщик, сумма и срок поставки **на дату проверки**. У каждого значения есть файл-источник, точная цитата и ссылка на абзац исходного текста. Несогласованные изменения показываются отдельно, отсутствующие значения — как «нет данных».

## Установка и запуск

Нужен Python 3.10+ (проверено на 3.14). Платные сервисы, ключи и интернет для работы не нужны.

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows;  macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
streamlit run app.py
```

Откроется http://localhost:8501. Тесты: `pytest -q`.

**Зависимости:** `streamlit` (интерфейс), `pytest` (тесты). Логика извлечения — стандартная библиотека Python (`re`, `datetime`).

## Как пользоваться

1. Слева загрузите документы любым способом (способы можно совмещать):
   - **несколько файлов сразу** — выделите их в окне выбора (Ctrl+клик / Ctrl+A) или перетащите группой;
   - **ZIP-архив** — извлекаются все TXT, включая вложенные папки; имена в CP866 (архиваторы Windows) читаются корректно;
   - **папку целиком** — поле «Или папка целиком», берутся все TXT и ZIP из папки и подпапок.

   Файлы других форматов, служебные (`.DS_Store`, `__MACOSX`) и дубликаты по содержимому пропускаются — список загруженного и пропущенного виден в блоке «Загруженные документы». Без загрузки можно оставить галочку «учебный комплект» — подхватится папка `documents/`.
2. Укажите дату проверки (по умолчанию 10.03.2026).
3. **Сводная таблица** — сумма и срок; бейдж «изменено: ДС № …», если значение изменено допсоглашением; оранжевые бейджи «не согласовано» — предложения из проектов и писем.
4. **Вопросы** — четыре кнопки с вопросами из задания или свой запрос: `сумма STN-102`, `срок STN-101`, `поставки раньше 01.04.2026`.
5. Любая ссылка «↗» прокручивает к абзацу исходного документа и подсвечивает его.

Ответы на учебном комплекте:

| Вопрос | Ответ | Основание |
|---|---|---|
| Срок STN-101 на 10.03.2026 | 30.04.2026 | ДС № 1 (подписано, в силе с 01.03.2026); проект ДС № 2 (10.05.2026) — не согласован |
| Сумма STN-102 | 840 000 ₽ | п. 2.1; аванс 252 000 входит в сумму и не прибавляется |
| Сумма STN-103 | нет данных | стоимость — в приложении № 1, его нет; 600 000 — бюджетный лимит, не цена |
| Поставки раньше 01.04.2026 | STN-102 (20.03.2026) | есть несогласованный перенос на 27.03.2026 (письмо поставщика) |

## Известные ограничения

- Извлечение на правилах: формулировки должны быть близки к учебным («общая стоимость … составляет N рублей», «поставить … не позднее ДД.ММ.ГГГГ», «вступает в силу ДД.ММ.ГГГГ»). Другая формулировка → «нет данных» или флаг «требует проверки», но не выдуманное значение.
- Абзац = непустая строка файла. Текст с жёсткими переносами внутри предложения может не распознаться.
- Связь документов — по номеру договора вида `ABC-123` в тексте. Документ без номера попадает в предупреждения.
- Суммы — только в рублях; «тыс. руб.», валюта и прописью без цифр не поддерживаются.
- Даты — только в формате ДД.ММ.ГГГГ (в текстовом запросе также «1 апреля 2026»).
- Текстовый запрос — разбор правилами, не свободный чат.
- Загрузка: не более 500 документов и 50 МБ распакованного текста за раз; зашифрованные ZIP и вложенные архивы (ZIP в ZIP) не поддерживаются.
- Состояние не сохраняется между сессиями; OCR, PDF/DOCX, права доступа — вне объёма.

# Записка

## Для кого

Специалист по закупкам, который сверяет сумму и срок поставки по десяткам договоров и не хочет перечитывать всю цепочку «договор → ДС → письма». Ему важно не столько «быстро», сколько **не ошибиться и уметь показать, откуда цифра**. Поэтому каждое значение подтверждается цитатой, а спорные случаи помечаются, а не угадываются.

## Пять вопросов клиенту перед развитием

1. В каком виде документы приходят на самом деле: сканы, PDF, DOCX, ЭДО (Диадок/СБИС), 1С? Сколько их в месяц?
2. Как в системе фиксируется факт подписания и вступления в силу: отметка в ЭДО, подпись на скане, статус в учётной системе? Кому доверять при расхождении?
3. Какие поля нужны после суммы и срока: неустойка, условия оплаты, аванс, этапы/частичные поставки, спецификации?
4. Что пользователь делает с результатом дальше — контроль сроков, претензии, отчёт руководству, выгрузка в 1С/ERP? Нужны ли уведомления о приближении срока?
5. Какая цена ошибки и кто отвечает за финальную проверку: допустим ли автоматический ответ или всегда нужен человек «в контуре»?

## Принятые допущения

- Условия меняет только ДС, у которого в статусе есть «подписано обеими сторонами» **и** указана дата вступления в силу ≤ даты проверки. ДС без даты вступления в силу не применяется и помечается «требует проверки» (по п. 5.1 договоров дата обязательна).
- Несколько вступивших ДС применяются по дате вступления в силу, затем по дате документа. Имя файла и порядок загрузки не важны.
- Письма и проекты никогда не меняют условия — только показываются как «не согласовано».
- Сумма — только «общая стоимость/цена договора» с числом и валютой. Авансы, лимиты, неустойки не подставляются.
- Срок поставки — только формулировки про поставку; сроки оплаты и приёмки игнорируются.
- Если в одном документе найдено несколько разных значений поля — значение не выбирается, ставится флаг.

## Две метрики

1. **Точность с источником** — доля полей, где значение совпало с эталоном *и* цитата указывает на верный абзац (на размеченной выборке). Цель — ≥ 98 %; «нет данных» вместо верного значения считается промахом, выдуманное значение — критической ошибкой (цель — 0).
2. **Время сверки одного договора** — от открытия до подтверждённого ответа, до/после внедрения (замер на пользователях). Дополнительно — доля флагов «требует проверки», которые пользователь закрыл без правок (если высокая — правила слишком осторожны).

## Архитектура

```
TXT / ZIP / папка ─► collect_files: распаковка, фильтр, дедупликация, лимиты
          ─► decode (UTF-8 / CP1251)
          ─► parse_document: абзацы, тип (договор/ДС/проект/письмо),
                             статус, дата вступления в силу, ссылки на договоры
          ─► analyze(дата проверки):
               договор: сумма, срок, поставщик (+ Evidence: файл, абзац, фрагмент)
               связанные документы по номеру договора
               ДС подписано и вступило ─► применить по дате вступления
               иначе ─► PendingChange (не согласовано)
               неоднозначность ─► flags (требует проверки)
          ─► answer_question / Streamlit UI (таблица, вопросы, источники с якорями)
```

`extractor.py` — вся логика извлечения, без зависимостей от интерфейса; `loader.py` — сбор файлов из ZIP и папок; `app.py` — Streamlit; `tests/` — 26 тестов.

### Три ключевых решения и компромиссы

1. **Правила и regex вместо LLM.** Плюс: детерминированно, бесплатно, работает офлайн, цитата — это буквально совпавший абзац, поэтому галлюцинации невозможны по построению. Минус: хрупко к перефразированию; каждый новый вид формулировки — новое правило.
2. **«Сомневаешься — не применяй, а пометь».** ДС без статуса или даты вступления в силу, противоречивые значения, несвязанные документы дают флаг, а не догадку. Плюс: нет тихих ошибок. Минус: больше ручной работы на «грязных» данных.
3. **Evidence как обязательная часть значения.** Значение без абзаца-источника в модели существовать не может. Плюс: проверяемость и простая подсветка в UI. Минус: значения, собранные из нескольких абзацев (например, «сумма = спецификация + доставка»), прототип не поддерживает.

### Что изменится при 100 000 документов и правах доступа

- Разбор переходит из интерфейса в фоновый конвейер (очередь + воркеры), результаты — в БД (PostgreSQL): документы, абзацы, извлечённые поля с evidence, связи «договор ↔ документ», версии.
- Связывание — не только по номеру, но и по контрагенту/ИНН и датам; появляется полнотекстовый поиск (OpenSearch/pg_trgm).
- Извлечение — гибрид: правила как быстрый и точный первый проход, LLM/NER для нераспознанных формулировок, **с обязательной проверкой, что цитата дословно есть в тексте**; спорное — в очередь ручной верификации.
- Права доступа — фильтрация на уровне запросов к БД (договоры по подразделениям/контрагентам, RLS), аудит просмотров и правок, ссылки на источники открываются только при наличии прав на исходный файл.
- Регрессия качества — размеченный эталонный набор и метрика точности в CI.

### Три следующих улучшения (по приоритету)

1. **Ручное подтверждение и правка значения** с сохранением, кто и на основании чего изменил — превращает прототип в рабочий инструмент.
2. **Новые поля: неустойка, условия оплаты, аванс** — та же схема «паттерн → Evidence → тест»; неустойка нужна для претензий по просрочке.
3. **Поддержка DOCX/PDF с текстовым слоем и нестрогих формулировок** (гибрид с локальной LLM с проверкой цитаты).

**Характерные запросы к ИИ:**
1. «Изучи вордовский документ и задай мне вопросы» — ИИ прочитал задание и учебные файлы, заранее выписал ловушки (аванс в STN-102, лимит в STN-103, срок оплаты vs поставки, проект ДС № 2) и задал вопросы о подходе, стеке, авторстве README и расположении проекта.
2. «Перейти на Streamlit» — после того как ИИ обнаружил, что Node.js на машине не установлен, стек сменили с Vite/React на Python + Streamlit, не теряя логики.
3. _добавить свой запрос — например, про проверку/правку результата_

**Ошибки и неудачные решения ИИ, как обнаружены и исправлены:**
- При извлечении текста из `.docx` ИИ дважды выводил русский текст прямо в консоль Windows и получал «кракозябры» (кодировка консоли). Исправление — запись в UTF-8 файл и чтение файла. Вывод: результат ИИ нужно проверять глазами, а не доверять тому, что «команда отработала».
- При запуске превью ИИ поднял чужой сервер из `launch.json` родительской папки (статический сайт другого проекта) вместо прототипа. Заметил по имени сервера в ответе инструмента, остановил и добавил отдельную конфигурацию.
- Тест на ZIP с русскими именами в CP866 сначала упал: ИИ собрал фикстуру через стандартный `zipfile`, который сам перекодирует не-ASCII имя в UTF-8, — то есть тест проверял не тот случай. Ошибка была в тесте, а не в коде; фикстура переписана так, чтобы в архив попадали именно байты CP866.
- Первая версия выбора полей в текстовом запросе была написана запутанным однострочником с побочным эффектом внутри условного выражения; работала, но читалась плохо — переписана явно до написания тестов.

**Как проверялся результат:**
- 26 автотестов: загрузка ZIP/папок (вложенные папки, мусорные файлы, дубликаты, битый архив, имена в CP866), четыре вопроса задания, «нет данных», статусы (подписано одной стороной, без статуса, вступает в силу позже), порядок ДС не по имени файла, новый договор того же формата с другими значениями, подмена поля, CP1251.
- Мутационная проверка: правило «подписано обеими сторонами» намеренно ломалось в памяти — 2 теста упали, т. е. тесты действительно ловят нарушение ключевого правила.
- Ручная проверка в браузере: таблица, кнопка вопроса 4, переход по ссылке «↗» к абзацу с подсветкой.
